Exact resolved package lists: `docs/pins/` (conda env exports, added after G1).
| torchcodec (cluster train env) | ==0.5 | **The pin lerobot 0.4.4 ships is the bug**: it requires `torchcodec>=0.2.1,<0.11.0`, which resolves to 0.10.0 -- built against torch 2.10 while we pin torch 2.7.0. 0.10.0 fails to load with `libtorchcodec_core6.so: undefined symbol: _ZN3c1013MessageLogger6streamB5cxx11Ev` (a libtorch ABI symbol, NOT an ffmpeg problem). 0.7.0 imports but its custom ops are still broken (`no fallback function is registered for schema torchcodec_ns::_convert_to_tensor`) -- an ABI mismatch that only shows up on first decode, so "it imports" is not evidence. torchcodec minor tracks torch minor for 0.3-0.5<->2.7. | verified 2026-08-19: decodes, and returns frames **bit-identical** to pyav (40 fetches, max abs pixel diff 0.0) |
| ffmpeg (cluster train env) | conda-forge `=6.*` | torchcodec bundles no ffmpeg (rejected on GPL grounds) and RHEL 8.8 ships no ffmpeg shared libs. Pin the MAJOR: a bare `conda install ffmpeg` now resolves to 9.x, whose `libavutil.so.61` no torchcodec wheel below 0.16 supports. Mapping to remember: `libavutil major = ffmpeg major + 52` (.56=FF4, .58=FF6, .61=FF9). torchcodec probes its variants in DESCENDING ffmpeg order, so the `libavutil.so.56` line in the traceback is the LAST attempt, not the real error. | installed+verified |
| LD_LIBRARY_PATH (cluster) | `$CONDA_PREFIX/lib` prepended | `libtorchcodec_core*.so` carries no RPATH/RUNPATH and dlopens ffmpeg by soname, so conda's own libs are invisible to it -- torchcodec reports "FFmpeg is not properly installed" with ffmpeg sitting in the same env. Exported in `train.sbatch`, `smoke_dataloader.sbatch`, `smoke_resume.sbatch`. | verified 2026-08-19 |
| video_backend (cluster train) | torchcodec | ~45x cheaper per frame fetch than pyav on a compute node (25.5 ms -> 0.57 ms) because torchcodec keeps a module-level `_default_decoder_cache`, while 0.4.4's pyav path rebuilds a `torchvision.io.VideoReader` for EVERY fetch on an 82,916-frame container. Local eval env stays on pyav -- eval renders from Isaac and never decodes video, so the two sides need not match here. | see G5a |
| LeRobot upgrade to 0.5/0.6 | REJECTED | 0.5.0's `datasets/video_utils.py` is byte-identical to 0.4.4 (its blog speedups are all record-side): zero gain. 0.6.x gives 3.7x on pyav (measured on our L0) but needs py>=3.12, which breaks the single-env property Isaac Sim 5.1 forces (G1b), silently flips five diffusion defaults (PR #3202: horizon 16->64, n_action_steps 8->32, use_group_norm True->False, pretrained_backbone_weights None->ImageNet, use_separate_rgb_encoder_per_camera False->True), and its checkpoints need two config keys stripped to load in 0.4.4. Fixing the torchcodec pin is a larger win (45x) for one line. | decided 2026-08-19, D23 |
| DiffusionConfig default deltas 0.4.4 -> 0.6.1 | 6 deltas; 5 land in 0.6.0, 1 in 0.6.1 | Full-source diff of `policies/diffusion/configuration_diffusion.py` across 0.4.4 / 0.5.0 / 0.5.1 / 0.6.0 / 0.6.1, all 29 DP defaults tabulated. (a) **0.5.0 and 0.5.1 are identical to 0.4.4 on every DP default** -- the rejected 0.5 bump was architecturally a no-op, not just a perf no-op. (b) All five flips in the row above land in **0.6.0**. (c) `gradient_checkpointing: bool = False` is a NEW field in **0.6.1** only -- behaviour-neutral, the 6th delta. (d) NOT changed, contrary to an earlier claim of mine: `do_mask_loss_for_padding` is `False` in every version from 0.4.4 to 0.6.1, so its pin in `diffusion_base.sh` is purely defensive and counters no flip. (e) `drop_n_last_frames` stayed **7** while horizon went 16->64, so 0.6.x's own inline formula comment (`horizon - n_action_steps - n_obs_steps + 1` = 31) contradicts its own default -- an upstream inconsistency, irrelevant to us because we pin both. Everything else (optimizer preset 1e-4/(0.95,0.999)/wd 1e-6, cosine + 500 warmup, DDPM/100/squaredcos_cap_v2, epsilon, clip_sample, crop_is_random, resnet18, down_dims, FiLM, 32 keypoints, num_inference_steps=None) is unchanged across all five releases. | verified 2026-08-19 by source diff |
| Version-bump failure mode is LOUD (given our pins) | ValueError, not silent drift | `modeling_diffusion.py:507-511` (0.6.1; :481-485 in 0.4.4) raises `"You can't replace BatchNorm in a pretrained model without ruining the weights!"` when `use_group_norm=True` AND `pretrained_backbone_weights` is set. The three encoder flips are therefore **coupled**: 0.6.0 had to set `use_group_norm=False` in order to turn the ImageNet weights on by default. Because `diffusion_base.sh` pins `use_group_norm=true`, a bump to 0.6.x would hit that ValueError at model construction rather than silently train a different architecture. That is the concrete justification for leaving `pretrained_backbone_weights` unpinned (passing None through draccus risks decoding the string "null"). | verified 2026-08-19 |
